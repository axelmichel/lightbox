# Lightbox

A Swift/SwiftUI app for Mac and iPad that generates pictures with a ComfyUI server and keeps them in a gallery with their full settings. Build, run and test commands: `README.md`.

## Structure
- Code goes in the local packages under `Packages/`. `App/` holds only the `@main` entry.
- Dependencies point one way: `LightboxUI → ComfyKit, LightboxCore`. ComfyKit and LightboxCore don't use SwiftUI and don't depend on each other; ComfyKit depends on nothing.
- The app icon is an Icon Composer file, `App/AppIcon.icon`; its source logo is in `Design/`.
- `Lightbox.xcodeproj` is generated by XcodeGen from `project.yml`. Edit `project.yml`, then run `xcodegen`; don't edit the project in Xcode. New package files need no project change.
- Gallery storage: `docs/GALLERY_FORMAT.md`. Change it together with `LightboxCore/Gallery.swift`.
- Compositions (the editor): `LightboxCore/Composition.swift` (layers, flatten, `CompositionStore`) and `MagicWand.swift`; UI in `LightboxUI/Compose*.swift`. Layers keep their own copy of the picture; the wand writes a new image id so undo works. The preview (SwiftUI) and `flatten` (Core Graphics) must draw the same. Inpainting crops and scales on the device (`Inpaint.swift`) and sends only that part; the result is blended back there.
- Node editor (ComfyUI-compatible): ComfyKit reads and writes the UI format (`WorkflowDocument.swift`, schema 0.4 and 1, subgraphs; unknown fields are kept so files round-trip), maps `widgets_values` to inputs from `/object_info` (`WidgetLayout.swift`), and turns a document into the API format like ComfyUI's frontend (`WorkflowCompile.swift`: mute, bypass, reroutes, primitives, notes, subgraphs as "outer:inner" ids). `ApiLayout.swift` reads API-format files; `WorkflowRun.swift` runs any graph with per-node events. Workflows are stored by `LightboxCore/WorkflowStore.swift`. The old editor UI was removed (it crashed and was untested); a new one coupled to the configurator is being built step by step after `docs/NODE_EDITOR_PLAN.md`. Its geometry is `LightboxUI/NodeLayout.swift` (LiteGraph metrics: `position` is the body's top left, the title sits above), with tests and no SwiftUI. Keep `NodeGraph` the same for the root graph and subgraphs. Test against `Fixtures/workflow_sdxl_frontend.json` (saved by ComfyUI's frontend 1.49.6) and `object_info_editor.json`.
- Picture formats: `AspectRatio` (`AspectRatio.swift`) gives each format's size per model family; `Detection.apply` uses it too.

## Conventions
- The repository is public. Never commit file names, metadata, prompts or pictures from a real install, server or gallery: fixtures and tests use made-up names (keeping the fragments detection needs). Check `git diff --cached` for this before every commit.
- Swift 6 language mode with strict concurrency. Models are `@MainActor @Observable`; ComfyKit and LightboxCore types are `Sendable` value types.
- Signing: team and bundle ID come from the git-ignored `Config/Local.xcconfig` (see README). Don't set the team in Xcode's Signing UI.
- Tests use Swift Testing (`import Testing`).
- Run `swift format lint -r App Packages` (config in `.swift-format`: 4 spaces, 120 columns).

## Preset detection (`LightboxCore/Detect.swift`)
- `PresetDetector.detect` guesses family, style and speed from the checkpoint's header metadata (`ComfyClient.modelMetadata`), its file name and the LoRAs in use; `Detection.apply` sets the matching sampling, size and prompt defaults.
- Each guess adds a note saying what it was based on; the preset editor shows them. Keep that when adding rules.
- LoRAs: `LoraDetector` (`LoraDetect.swift`) reads the trigger words (`modelspec.trigger_phrase`, kohya folder names, training tags in nearly every picture that aren't common Danbooru or quality tags), the family it was trained for and a starting strength. Test against `Fixtures/lora_metadata.json` (made-up LoRAs with neutral tags); add new made-up cases there.
- New model names go into `Fragments`, with a case in `detectsFamilyAndStyle`.
- Flux, Flux 2 and Z-Image are split models (`ModelFamily.isSplit`); Flux 2 samples with `SamplerCustomAdvanced` + `Flux2Scheduler` (`SplitModelRequest.Sampling.flux2`), so FaceDetailer is skipped for it: `checkpoint` holds the diffusion model, plus `textEncoders`, `vae`, `guidance` (Flux) and `shift` (Z-Image). `SplitParts` picks encoders and VAE by name; `Detection.applySplit` sets their sampling. `GenerationPreset.request` (`LightboxUI/PresetRequest.swift`) is the one place a preset becomes a `GenerationRequest`; `problem(with:)` says what is missing. Test cases: `flux1-krea-Q4.gguf`, `flux-2-klein-9b-Q4.gguf` and `z_image_turbo-Q4.gguf`, and the workflows in `Fixtures/workflow_flux_ui.json` / `workflow_flux2_ui.json` / `workflow_zimage_ui.json`. Fragments of up to three letters, or starting with `=`, match whole tokens only, so "art" doesn't match "smart".

## Content guard (`LightboxCore/Guard.swift`)
- Pictures of children are allowed. Sexualizing minors is never allowed.
- Every prompt sent to ComfyUI goes through `compose()`, which calls `ContentGuard.check`. Don't add a code path that builds a `GenerationRequest` from user text without going through it. Reusing a recipe goes through `compose()` again. The editor's *Edit with Model*, *Redraw Area* and *Edit with Instruction* (`ComposeDocument`) do too.
- Changes to the term lists need tests in both directions: a minor plus a sexual term is blocked, and normal scenes with kids pass.
- Anything that queues a node-editor workflow (`WorkflowCompiler` output) must put every text value through `ContentGuard.check` (positive, or negative if it only reaches `negative` inputs; `CompiledWorkflow.texts`) with the LoRA names, and add the forced negatives (`addNegative`).
- Style modifiers (`StyleModifier.swift`) are added to the prompt by `compose()` and checked by the guard like the rest of it. Built-ins have fixed UUIDs; don't renumber them.
- The prompt helper (`Enhance.swift`, `Ollama.swift`) only writes a suggestion. The user puts it into the prompt field, and it is composed and guarded from there. Never send Ollama output to ComfyUI directly.

## ComfyUI
- Workflows are built in code (`WorkflowBuilder`), not from JSON templates.
- `WorkflowBuilder.build` also gives every node a `NodeRole` (`WorkflowRoles.swift`) and the chain ends (`Anchor`) for the node editor; `txt2img` is its graph. `WorkflowDocument(built, catalog:)` (`WorkflowProjection.swift`) lays it out as a document with each role in the node's `properties` (`lightbox_role`); compiled again it must give the same graph (`projectionCompilesToTheBuiltGraph`). `ManagedGraph` (`WorkflowReading.swift`) reads the values by role back from a document and lists missing required roles; its `settings` must equal `GraphSettings(request)` for an unchanged graph. `Fixtures/built` holds the API graphs it must keep producing (`builtGraphsStayTheSame`); re-record them with `RECORD_BUILT=1` only when the graph is meant to change.
- Only use node inputs the server reports in `/object_info`. Unknown linked inputs break older servers. See `ComfyCatalog.controlNetTakesVAE`.
- Results use `PreviewImage`, which saves to ComfyUI's temp folder; Lightbox keeps its own copy in the gallery.
- Nodes with many inputs (`FaceDetailer`, `IPAdapterAdvanced`) are added with `defaultsFrom: catalog`. Set only the inputs that matter.
- `Fixtures/object_info.json` is cut down from a Krita-style server. When regenerating it from a live `/object_info`, keep the node definitions but replace the model lists with the made-up test cases.
- `WorkflowImport` turns a ComfyUI workflow (API or UI format) into a preset; it doesn't run the graph. UI-format widget values have no names in the file; `widgetNames` lists their order for the nodes it reads. Add new nodes there, with a test.
- Guides are chosen by purpose (`ControlKind`). `ControlResolver` maps a kind and architecture to models by file name; `ModelFamily.arch` (`GuideInfo.swift`) maps a preset's family to an architecture. Add new models in `ControlResolver`, with a test in `resolvesGuidesByPurpose`.
- ComfyKit has no app-specific code. Lightbox added `uploadFolder`, `modelMetadata`, inpainting (`InpaintSource`, `canInpaint`) and split models (`SplitModelRequest`, `diffusionModels`, `textEncoders`).
